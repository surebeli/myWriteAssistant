## 1. Why this spec exists

Current state of `myWriteAssistant`：AI provider 在两个 API route 里通过 `process.env.DOUBAO_*` 直接初始化 `createOpenAI`，前端 settings 里虽然有 `provider: 'openai' | 'anthropic' | 'custom'` 字段但**完全没被服务端读取**——这意味着用户在 UI 改 provider 不生效，事实上锁死 Doubao。

v0.2 的目标是把这层锁打开：让用户能**真实选择**调用哪家 LLM，并能**看到自己花了多少钱**。这同时也是 myWriteAssistant 自身的产品差异化（"Notion-for-writing 加多 LLM 路由"），不只是为了 hopper dogfood。

## 2. Goals (in scope)

1. **Provider 抽象**：`AIProvider` interface（含 capability + usage + error contract + prepareMessages）+ adapter registry，支持 Doubao / Claude / OpenAI / Kimi / DeepSeek 五家 v0.2 首发
2. **Per-scenario routing**：用户可以让 Chat 用 A、Proactive 用 B（v0.2 仅这两个 scenario）；同时支持"全部用一个"作为简单模式
3. **凭据安全**：API key 在 Tauri 桌面端走 secure storage，在 Web 模式走 localStorage 加显式风险提示；**transport 路径同时受保护**（无日志 / 无 DevTools / 无 error 泄露）。**注意**：本项目仅声明 at-rest + transport 安全，**不**声明 renderer runtime memory 安全（见 R12）
4. **请求驱动配置**：`/api/chat` 和 `/api/proactive` 不再读 `process.env`，配置完全从 client payload 来；**所有 client 通过单一 `resolveProviderConfig` 函数取 config**，禁止多处自拼
5. **Cost observability（minimal）**：每次 LLM 调用记录 `AICallRecord` 到 IndexedDB；产品内出 **table-only** cost 仪表盘
6. **Provider 状态可见**：状态栏读 store，不再硬编码"豆包 API"；message bubble 标注本条由哪个 provider 产出

## 3. Non-goals (explicit out of scope)

以下事项 Researcher 在 audit Section 3 里指出存在偏差，但**本次不修**：

- ❌ PromptBuilder 三层架构（Meta + Task + Context）—— 推到 v0.3
- ❌ IndexedDB 向量缓存与语义搜索 —— 推到 v0.3（v0.2 保留 MiniSearch 全文搜索）
- ❌ Proactive 模式的 content hash 去重 —— 推到 v0.2.1
- ❌ Proactive 返回结构化 JSON `{s, r, c}` —— 推到 v0.2.1（**但**：v0.2 在切换非 Doubao 时若发现纯文本回退失败，要在 chat-panel 输出"格式异常"占位，不能崩 UI）
- ❌ 与 provider 抽象**无关**的产品扩展（导出格式、协作、移动端等）
- ❌ Phase 5 Proactive polish、Phase 6 Tauri 功能扩展（只确保能 build）
- ❌ 真正的测试框架（v0.2 只要求一个手动 smoke 脚本 + 路由集成测试 + 几条针对 sanitizer / 去重的 E2E）
- ❌ **`summary` scenario**（Critic v1 Issue 3 修订）：原 v1 误把 summary 列入 AIScenario 但 repo 无 `/api/summary` 路由，会造成死配置。v0.2 删掉，推 v0.3 一起做（含 route + UI 入口 + per-scenario AC 扩展）

> **关于"新功能"的边界**：cost observability（D6 / §7 AC6-AC7）虽在 v0.1 不存在，属于 vendor-agnostic 重构的**直接配套基础设施**——让"省钱"卖点可验证——不视为"新功能"。本节排除的是与 provider 抽象**无关**的产品扩展。

> **Cost dashboard scope hard limit**：v0.2 仅做 **table-only** 三视图（按 provider / scenario / day），**不做** pricing override UI、不做图表组件、不做导出。这些推到 v0.2.1。

任何 PR 触碰 ❌ 列出的事项 → 直接 reject，不进 review。

## 4. Decisions

### D1：API key 传输方式

**决定**：API route 完全无状态。每次请求由 client 把 `providerConfig` 放进 payload。

**细节**：

- Request payload schema 见 §5.3
- Client 取 config 走单一函数 `resolveProviderConfig`（见 §5.3.1），**禁止**任何其他位置自拼
- API route **删除**所有 `process.env.DOUBAO_*` 读取代码（v0.2 不留 fallback——pre-1.0 没有兼容包袱）
- `.env.example` 移除 Doubao 相关环境变量；同时新增 `.env.example` 的注释说明"v0.2 起 API key 由用户在产品 Settings 内填写，非环境变量"

**理由**：本应用是本地 Tauri 应用，无公网拦截风险；无状态 API 简化架构；让"用户填的 key 真的生效"成为产品事实。

> **重要**：D1 只解决 storage→API 的传递路径选择，**不**自动等同 transport 安全或 renderer memory 安全。Transport 侧由 D7 全面覆盖；renderer memory 见 R12。

### D2：是否全盘对齐 Vercel AI SDK + ship gate（v2 修订）

**决定**：是，所有 provider 通过 AI SDK 接入。**v0.2 ship gate 硬规则**：5 家 stable provider 的 smoke 测试必须全部 pass，**不允许** experimental provider 进入 v0.2 首发。

**细节**：

- 仅 System + User messages，不在 v0.2 引入多轮 tool calls
- 每加一个 provider 前先用 1-script smoke test（见 T13）验证 SDK 兼容性
- **CI smoke 模式**：`npm run smoke:providers -- --require-all-stable` 必须 5 家全 pass。任一缺 key 或失败即 v0.2 release **block**。Local dev 可以 skip 单家，但 CI ship gate 不允许 skip
- 如果某 provider 在 v0.2 周期内 SDK 兼容失败：从 5 家首发名单中**移除**该家，发 4 家版本；**不允许** "experimental but shipped" 的折衷
- AC3 与 D2 现完全一致：5 stable + 5 smoke pass，无例外

> Critic v0 → v1 → v2 的演进：v0 提了 "experimental" 概念但模糊；v1 试图保留 experimental 但加 AC3 排除，被指自相矛盾；v2 直接砍掉 experimental shipping，只剩 stable 通道，gate 干净。

### D3：是否本次修 PromptBuilder

**决定**：不修。Researcher 倾向正确，确认 defer 到 v0.3。

**细节**：v0.2 保留当前的内联字符串模板。但要求 Builder **把 prompt 字符串集中到一个 const 文件**（`src/lib/ai/prompts.ts`）而不是散落在 route 里——这是 v0.3 重构 PromptBuilder 时的预备动作，几乎零成本。

### D4：默认行为与首次启动

**决定**：首次启动且没有任何 provider 配置时，Settings 显示空状态引导用户填配置；Chat / Proactive 入口禁用并提示"请先配置 AI provider"。

**理由**：避免空配置时调 API 报 500 的体验崩坏。

### D5：Per-scenario 默认值

**决定**：默认所有场景共用一个 provider 配置（"simple mode"）；用户在 Settings 中开启 "advanced mode" 才暴露 per-scenario 配置。

**细节**：v0.2 仅 chat 与 proactive 两个 scenario（见 §3 删除 summary 的说明）。

**理由**：保持 onboarding 单纯。

### D6：Cost observability 协议（v2 修订：cancellation 路径明确）

**决定**：v0.2 必须落地 cost 记录与 minimal dashboard；dashboard 范围受 §3 约束（table-only / 无 override / 无图表 / 无导出）。

**统一响应协议**：

- 每个 chat / proactive route **必须**在最终 SSE `finish` event 或 non-streaming JSON response 末尾返回：
  ```typescript
  usage: {
    tokensIn: number | null,
    tokensOut: number | null,
    model: string,
    providerId: AIProviderId,
    scenario: AIScenario,
    latencyMs: number,
    requestId: string,
    status: 'success' | 'failure',  // server side only sees these two
  }
  ```
- 当 provider 上游不返回 usage 时，记录 `tokensIn/tokensOut = null`、`tokensUnknown: true`，**不写 0**
- **Cancellation 路径**（Critic v1 Issue 4 修订）：
  - 用户点击"停止生成"或关闭面板触发 `AbortController.abort()` → fetch 连接断开 → server finish event **可能不会**到达 client
  - 因此 **client 端 abort handler 直接写一条 `AICallRecord(status='cancelled', tokensUnknown=true, latencyMs=已用时间)`**，不依赖 server finish
  - server 端如能感知 abort（例如 streaming 中途断开），记 server-side log 但**不**作为 client cost record 的来源
  - AC6 必须覆盖三条 status 路径：success / failure / cancelled，每条至少一条 E2E
- Client 收到 finish event（success/failure 路径）后写 IndexedDB（新增 store `ai_calls`），用 `requestId` 作为 idempotency key
- Pricing：`src/lib/ai/pricing.ts` 是只读硬编码每家 token 价格表；v0.2 用户**不能修改**；model override 指向未列价 model 时显示 `estimatedUsd: undefined` + "price unknown"，**不**套 default price（R14）

### D7：API key 凭据保护（Storage + Transport，**不含 renderer memory**）

**Storage 层**：

- Tauri 模式：用 `tauri-plugin-store` + OS keyring（具体由 Builder T14-spike 决定）
- Web 模式：localStorage + Settings 页面置顶警告"Web mode stores keys in localStorage; for production use the desktop app"
- store 层提供统一的 `keyStorage.get(providerId)` / `.set()` / `.delete()`，UI 不感知底层

**Transport 层**：

- 生产 Tauri build **必须禁用 DevTools**（`tauri.conf.json` 中 `app.security.devtools = false` 或等价配置；T14-impl 配置）
- API route 实现层禁止任何把 request body 打到 console / 日志 / error reporting 的代码：
  - 在 `src/lib/ai/route-helpers.ts` 提供唯一允许的 logger，logger 内部 sanitize providerConfig
  - Builder 在 T02 加 ESLint custom rule 或 PR review checklist 项："route handler 不得直接 `console.log(req.*)`"
- API route 错误响应**只返回** `{ code, provider, requestId, message }`：
  - `message` 必须经过 `sanitizeProviderError()`（adapter 提供 `normalizeError`，registry 包一层全局 sanitizer）
  - upstream 错误对象不得直接 spread 到 response
- Crash reporter / telemetry（如未来引入）必须 redact request body
- E2E test：发请求时 mock console + capture response，断言 console 日志和 response error 中均不出现 `apiKey` 字符串（详见 AC9 / AC13）

**不在本次 scope**（Critic v1 Risk Gap 1 → R12）：

- React renderer 的 memory 安全：恶意 dependency / XSS / 调试扩展可在 fetch 前读到 `providerConfig.apiKey`
- 这是 Tauri 桌面应用 + 本地用户填 key 的 inherent 风险面，需要 CSP + no-remote-script + 长期方案（Tauri Rust sidecar 调 API）才能闭环
- v0.2 **明确不解决**这个；README "AI provider 配置"段必须显示这条 disclaimer

### 5.2 核心 interface（v2：增加 prepareMessages 让 capabilities 可执行）

```typescript
// src/lib/ai/types.ts
import type { LanguageModelV1 } from '@ai-sdk/provider';
import type { CoreMessage } from 'ai';

export type AIProviderId = 'doubao' | 'claude' | 'openai' | 'kimi' | 'deepseek';
export type AIScenario = 'chat' | 'proactive';   // v0.2 仅这两个；summary 推 v0.3

export interface AIProviderConfig {
  id: AIProviderId;
  apiKey: string;          // 仅在内存中流转，由 resolveProviderConfig 注入
  baseURL?: string;        // 用户可覆盖（本地代理等）
  model: string;           // 用户在该 provider 默认值上可改
}

export interface AIAdapterCapabilities {
  supportsSystem: boolean;            // 是否原生支持 system message（Anthropic 与 OpenAI 处理路径不同）
  streamingMode: 'sse' | 'json-stream' | 'none';
  defaultBaseURL: string;
  authStyle: 'bearer' | 'x-api-key' | 'custom';
}

export interface NormalizedUsage {
  tokensIn: number | null;            // null = 上游不返；写 IndexedDB 时 tokensUnknown=true
  tokensOut: number | null;
  modelEcho?: string;
}

export interface NormalizedError {
  code: string;             // provider-specific 或 'unknown'
  message: string;          // 已 sanitized，禁含 apiKey / Authorization header / raw upstream
}

/** 调整后准备喂给 streamText 的 system + messages */
export interface AdjustedRequest {
  system?: string;
  messages: CoreMessage[];
}

export interface AIAdapter {
  id: AIProviderId;
  name: string;
  defaultModels: string[];
  status: 'stable';                                  // v0.2 不允许 experimental（D2 v2）
  capabilities: AIAdapterCapabilities;

  /** 创建底层 model 实例（喂给 Vercel AI SDK 的 streamText） */
  createModel: (config: AIProviderConfig) => LanguageModelV1;

  /**
   * 根据 capabilities 把 (system, userMessages) 调整为 provider 实际接受的形式。
   * Default 行为（supportsSystem=true）: passthrough，原样返回。
   * 当 supportsSystem=false 时：把 system 内容 prepend 到第一条 user message。
   * 由 route-helpers.callAdapter() 调用，**route handler 不得自行决定**。
   */
  prepareMessages: (system: string | undefined, messages: CoreMessage[]) => AdjustedRequest;

  /** 从 Vercel AI SDK 的响应里取 usage（不同 provider 字段位置不同） */
  extractUsage: (rawResponse: unknown) => NormalizedUsage;

  /** 把 provider 抛出的 error 标准化为安全可展示的 shape */
  normalizeError: (err: unknown) => NormalizedError;
}

export interface AICallRecord {
  id: string;                                   // ULID（client 生成）
  provider: AIProviderId;
  scenario: AIScenario;
  model: string;
  tokensIn: number | null;
  tokensOut: number | null;
  tokensUnknown: boolean;
  latencyMs: number;
  timestamp: number;
  requestId: string;                            // idempotency key
  status: 'success' | 'failure' | 'cancelled';
  errorCode?: string;                           // 仅 status != success 时
  estimatedUsd?: number;                        // pricing.ts 算不出时 undefined（R14）
}
```

**Route 调用约定**（Critic v1 Issue 1 修订）：

```typescript
// src/lib/ai/route-helpers.ts
export async function callAdapter(
  adapter: AIAdapter,
  config: AIProviderConfig,
  system: string | undefined,
  messages: CoreMessage[],
) {
  const adjusted = adapter.prepareMessages(system, messages);
  return streamText({
    system: adjusted.system,
    messages: adjusted.messages,
    model: adapter.createModel(config),
  });
}
```

API route handler **只能** 通过 `callAdapter()` 走，禁止直接构造 `streamText({ system, messages, model: ... })`——否则 capabilities-driven 行为会被绕过。这是 AC16 验证目标。

### 5.3 Request payload schema

```typescript
// POST /api/chat 或 /api/proactive 的 body
{
  providerConfig: AIProviderConfig;
  scenario: AIScenario;               // 仅 'chat' | 'proactive'
  requestId: string;                  // client 生成 ULID
  messages: CoreMessage[];            // System + User
}

// Response 末端 metadata（streaming finish event 或 non-streaming JSON）：
{
  usage: {
    tokensIn: number | null,
    tokensOut: number | null,
    model: string,
    providerId: AIProviderId,
    scenario: AIScenario,
    latencyMs: number,
    requestId: string,
    status: 'success' | 'failure',
  }
}

// Cancellation：client abort 后 server 不发 finish event；client 自己写一条 status='cancelled' 记录到 IndexedDB（D6）

// Error response：
{
  error: {
    code: string,
    provider: AIProviderId,
    requestId: string,
    message: string,    // 已 sanitized
  }
}
```

### 5.3.1 Client Request Assembly Contract

**全 client 仅允许通过单一函数获取 `providerConfig`**：

```typescript
// src/lib/ai/request-assembly.ts
import { useSettingsStore } from '@/stores/settings-store';
import { keyStorage } from '@/lib/ai/key-storage';
import { getAdapter } from '@/lib/ai/registry';

export class MissingProviderConfigError extends Error {
  constructor(public providerId: AIProviderId) {
    super(`No API key configured for provider: ${providerId}`);
  }
}

export async function resolveProviderConfig(
  scenario: AIScenario
): Promise<AIProviderConfig> {
  const settings = useSettingsStore.getState().ai;
  const scenarioCfg = settings.mode === 'simple'
    ? settings.simple
    : settings.perScenario[scenario] ?? settings.simple;

  const apiKey = await keyStorage.get(scenarioCfg.providerId);
  if (!apiKey) throw new MissingProviderConfigError(scenarioCfg.providerId);

  const adapter = getAdapter(scenarioCfg.providerId);
  return {
    id: scenarioCfg.providerId,
    apiKey,
    model: scenarioCfg.modelOverride ?? adapter.defaultModels[0],
    baseURL: scenarioCfg.baseURLOverride,
  };
}

export function generateRequestId(): string {
  // ULID monotonic（防同毫秒多次调用碰撞）
}
```

**约束**：

- API route handler、Settings UI、Chat / Proactive panel、status bar 等任何位置**不得**自行从 settings + keyStorage 拼 config
- `resolveProviderConfig` 返回的 config 仅在内存中流转，不进 Zustand persist、不进 localStorage
- API route 收到 `providerConfig` 后，用完即丢；不缓存、不日志、不 echo
- requestId 由 client 在调用 `resolveProviderConfig` 之后立即生成，**全链路一致**——chat-panel 用同一个 requestId 写 IndexedDB（含 cancellation 路径）和发请求

## 6. Migration

### 6.1 用户侧（v2 修订：renderer 不能直接读 env）

Critic v1 Issue 2 指出原方案"在 renderer 检测 process.env"不可达。**必须有 server-side bridge**：

- v0.2 release notes 顶部显著说明："`DOUBAO_API_KEY` 环境变量不再生效"
- **首次启动检测流程**：
  1. Renderer 调 **migration bridge**：
     - Web 模式：调 `GET /api/migration/legacy-doubao-key`（Next API endpoint，server-side 读 `process.env.DOUBAO_API_KEY` 返回 `{found: true|false, masked: 'sk-***xyz'}`，**不**返回完整 key）
     - Tauri 桌面端：调 Tauri command `read_legacy_doubao_env`（Rust 侧读 env，相同响应 shape）
  2. Renderer 拿到 `{found: true, masked: '...'}` 且用户 settings 空 → 弹一次性 dialog "检测到旧 Doubao 配置 (sk-***xyz)，是否一次性导入到 secure storage？"
  3. 用户点"导入" → renderer 调第二个 bridge `POST /api/migration/import-legacy-doubao-key`（or Tauri command）→ server 读 env + 写 keyStorage（providerId='doubao'）+ 返回成功
  4. settings 设 `mode='simple'` + `simple.providerId='doubao'`，弹完不再提示
  5. 用户点"忽略" / 关闭 dialog → 不再提示，走空状态引导（D4）
- Bridge 实装由 **T18a (Builder)** 负责；dialog UI 由 **T18b (Builder-UI)** 负责
- 任何情况下**不静默自动迁移**——避免误带凭据

### 6.2 代码侧

- Doubao 现有调用 → adapter 之后，所有 import `@ai-sdk/openai` 仅在 `adapters/doubao.ts` 内出现
- API route 之后只 import `src/lib/ai/registry.ts`，通过 `registry.getAdapter(providerConfig.id).createModel(config)` 拿 model（包在 `callAdapter` 里）

### 6.3 回滚（v2 修订：不假装自动可回滚）

Critic v1 Issue 6 指出 "v0.1 forward-compat" 是已发布版本的要求，v0.2 分支无法保证。降级为手动回滚：

如果 v0.2 上线后发现严重问题，rollback checklist：

1. **代码层**：在 main 分支保留 v0.1 latest tag，回滚仅是 git revert / branch reset
2. **桌面安装包**：v0.1 安装包必须保留可下载（GitHub Release 不删旧版）；v0.2 ship 前 release notes 注明"如遇严重问题可回退到 v0.1，但需手动操作"
3. **Settings schema versioning**：v0.2 写 `schemaVersion: 2`；**不假设** v0.1 能读 schemaVersion=2 而不 throw。release notes 明确："如需回退，请先卸载 v0.2 + 清空 IndexedDB 与 settings → 安装 v0.1 → 重新填写 Doubao key"
4. **Key 导出工具**：T14-impl 提供 `npm run export-keys` 或产品内"导出配置"按钮，把已配置的 keys 导出为环境变量格式，方便用户回退后手动恢复
5. **Ship gate**：Tauri build 失败禁止标记 v0.2 已发；release 流程必须先 desktop build 通过再公布版本号

issue tracker（GitHub Issues）必须在 v0.2 ship 前建好，方便用户报回退后行为。

> 如未来 v0.2.x 周期内决定做"自动回退"，需要单独发 v0.1.x patch 提供 forward-compat 容错（独立 release，独立 task）。本 spec scope 不包含。
