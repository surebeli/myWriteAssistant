# 用 AI 帮我设计和开发一个 AI 写作助手

> 从痛点到产品：完整记录 MyWriteAssistant 的诞生过程

---

## 引言

这是一个关于"用 AI 做 AI 产品"的故事。

我要做一个 AI 写作助手。不是因为市场需要，而是因为我自己需要。

现有的工具——NotebookLM、Notion AI、各种 AI 写作助手——都有各自的问题。我决定自己动手，做一个真正符合我工作流的产品。

更有趣的是，整个设计过程都是和 AI 对话完成的。

这篇文章会完整记录：我为什么做这个、怎么想清楚要做什么、以及准备怎么做。

---

## 第一章：痛点

### 收藏夹焦虑症

作为内容创作者，我有一个习惯：疯狂收藏。

看到好文章，收藏。发现有用的 PDF，下载。读到精彩观点，记笔记。

结果就是：收藏夹里躺着几百篇文章，写作时一篇都想不起来。

这不是工具的问题，是工作流的问题。**收藏 ≠ 可用**。

### 现有工具的不足

我试过很多方案：

| 工具 | 我的体验 |
|------|----------|
| Notion | 笔记越多越乱，AI 功能太浅 |
| NotebookLM | 多文档问答很强，但不是写作工具 |
| Obsidian | 编辑体验好，但没有 AI |
| ChatGPT | 每次都要复制粘贴上下文 |

我想要的是：

> **一个编辑器，能自动知道我收藏过什么，在我写作时主动推荐相关素材，并且能实时润色我的句子。**

市面上没有，那就自己做。

## 第二章：设计过程

### 和 AI 做 Brainstorm

我用 Copilot 的 brainstorming skill 来梳理需求。

它的工作方式很有意思：**一次只问一个问题**。

> "你主要写什么类型的内容？"

技术博客、个人笔记、长文。

> "素材从哪来？"

网页、PDF、Markdown、自己的草稿。

> "你最希望 AI 帮你做什么？"

这个问题让我想了很久。最后我打了一大段：

> "基于素材总结核心要点，写作时根据我正在写的内容推荐相关文章。不要一开始就把所有素材塞给 AI，那样 token 太贵，效果也不好。"

这段话后来变成了产品的核心设计：**渐进式上下文加载**。

### 一个意外的创新

聊到 AI 助手的交互形式时，我突然有了一个想法。

传统 AI 助手是被动的——你问它答。但我不想写着写着停下来问 AI。

如果 AI 能**实时观察我在写什么**，然后**主动给建议**呢？

但又不能太打扰。于是我加了两个限制：

1. **延迟触发**：写完一个句子，等 1.5 秒再给建议
2. **句子粒度**：最多改一句话，不要大段改写

这就是 **Proactive 模式** 的诞生——AI 像一个坐在旁边的写作伙伴，安静观察，适时建议。

### 双模式设计

但有时候我确实需要主动问 AI：

- "帮我生成一个大纲"
- "推荐与这个话题相关的收藏"
- "把这段翻译成英文"

所以最终设计是**双模式**：

| 模式 | 场景 | 交互方式 |
|------|------|----------|
| **Proactive** | 专注写作 | AI 主动建议，不打扰 |
| **Chat** | 需要帮助 | 用户主动对话 |

默认 Proactive，一键切换 Chat。

## 第三章：技术架构

### 为什么是 Web 而不是桌面应用？

一开始我考虑过 Electron。本地应用嘛，文件访问更自然。

但后来发现 **File System Access API**——现代浏览器（Chrome/Edge）可以读写本地文件夹！

这意味着我可以：
- 用 Web 技术快速开发
- 保持本地存储（Markdown 明文）
- 未来可以轻松部署成 SaaS

### 技术栈

```
Framework:    Next.js 14 + TypeScript
UI:           Tailwind CSS + shadcn/ui
Editor:       Tiptap (ProseMirror)
Storage:      File System Access API + IndexedDB
AI:           豆包 API (OpenAI 兼容)
State:        Zustand
```

### 核心设计：渐进式上下文

```
┌─────────────────────────────────────────────────────────────┐
│                    文档处理流程                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  导入文档 ──→ AI 生成摘要（200字）+ 核心要点（5-7条）         │
│       │                  │                                  │
│       ▼                  ▼                                  │
│  原文存储             摘要缓存                               │
│  documents/          summaries/                             │
│                                                             │
│  写作时：                                                   │
│  1. 只匹配摘要（成本低）                                     │
│  2. 找到相关文档                                            │
│  3. 用户选择后才加载原文（按需深入）                         │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

这个设计的好处：
1. **省 Token**：不需要把所有文档塞给 AI
2. **更精准**：摘要是结构化的，匹配效果更好
3. **快速**：只加载需要的内容

### Proactive 模式实现

```typescript
// 核心逻辑伪代码
editor.on('update', debounce(async (text) => {
  // 1. 提取最后一个完整句子
  const sentence = extractLastSentence(text);
  if (!sentence || sentence.length < 10) return;
  
  // 2. 调用 AI 生成建议
  const suggestion = await generateSuggestion(sentence, context);
  
  // 3. 显示在侧边栏，等待用户决策
  showSuggestion(suggestion);
}, 1500)); // 延迟 1.5 秒

// 用户采纳
const accept = () => {
  editor.replaceCurrentSentence(suggestion);
  clearSuggestion();
};
```

## 第六章：反思

### 和 AI 对话的价值

这次经历让我重新理解了 AI 在创作中的角色。

AI 不是来替代思考的。它的价值是：**用问题引导你把模糊的想法具体化**。

"你想做什么？"
"为什么这样？"
"如果那样呢？"

一个个问题，逼着我把直觉变成设计。

### 为什么自己做

有人可能会问：市面上那么多工具，为什么非要自己做？

答案很简单：**最好的产品是为自己做的产品**。

因为你最了解需求，最能判断好坏，最有动力迭代。

如果它能解决我的问题，可能也能解决其他人的问题。
如果不能，至少我有了一个自己用着顺手的工具。
